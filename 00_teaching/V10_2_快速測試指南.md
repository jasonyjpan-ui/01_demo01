# V10.2 快速測試指南：完整菜單版本化

本指南用來確認 V10.2 的完整版本化模型是否正常運作。V10.2 的重點是：更新菜單不覆寫舊資料，而是建立新版本；訂單送出時會檢查購物車內的菜單版本是否已過期。

## 啟動方式

JSON store：

```powershell
cd bf1042
$env:STORE_DRIVER = "json"
npm run dev
```

PostgreSQL store：

```powershell
cd bf1042
bunx drizzle-kit migrate
$env:STORE_DRIVER = "postgres"
npm run dev
```

預設服務：

- 前端：http://localhost:5173
- 後端：http://localhost:3000

## 欄位語意

- `id`：每一個版本自己的資料列 ID。
- `logicalId`：同一個菜單品項共用的穩定 ID。
- `entityId`：跨環境同步用途的穩定識別。
- `version`：版本號，從 1 開始。
- `isCurrentVersion`：是否為目前可點餐版本。
- `supersedes`：此版本取代哪一個舊版本 ID。
- `previousPrice`：上一版價格。
- `changeReason`：變更原因。

## 測試 1：取得目前菜單

```bash
curl http://localhost:3000/api/menu/current
```

應該看到：

- 每個品項都有 `id`、`logicalId`、`entityId`、`version`。
- 只回傳 current version。
- 初始資料通常是 `version: 1`。

## 測試 2：更新菜單會建立新版本

假設品項 ID 1 目前是 version 1：

```bash
curl -X PATCH http://localhost:3000/api/menu/1 \
  -H "Content-Type: application/json" \
  -d '{"price": 45, "version": 1, "changeReason": "第一次調價"}'
```

應該看到：

```json
{
  "data": {
    "id": 13,
    "logicalId": 1,
    "version": 2,
    "isCurrentVersion": true,
    "supersedes": 1,
    "previousPrice": 40,
    "changeReason": "第一次調價"
  }
}
```

重點：

- 新版本有新的 `id`。
- `logicalId` 維持不變。
- `version` 從 1 變 2。
- `previousPrice` 會顯示舊價格。

## 測試 3：再更新一次會變 version 3

請使用上一個 response 回傳的新 `id` 與 `version`。假設新 id 是 13：

```bash
curl -X PATCH http://localhost:3000/api/menu/13 \
  -H "Content-Type: application/json" \
  -d '{"name": "新版測試品項", "version": 2, "changeReason": "修改品名"}'
```

應該看到：

- `version` 變成 3。
- `supersedes` 指向 version 2 的 ID。
- `logicalId` 仍然維持同一個值。

## 測試 4：查詢版本歷史

```bash
curl http://localhost:3000/api/menu/13/history
```

應該看到同一個 `logicalId` 的所有版本，通常由新到舊排序：

```json
{
  "data": [
    { "version": 3, "isCurrentVersion": true },
    { "version": 2, "isCurrentVersion": false },
    { "version": 1, "isCurrentVersion": false }
  ]
}
```

## 測試 5：目前菜單只會出現最新版本

```bash
curl http://localhost:3000/api/menu/current
```

同一個 `logicalId` 只應該看到最新的 current version，不應該同時看到 version 1、2、3。

## 測試 6：舊版本更新會回 409

如果 ID 1 已經不是 current version，再用它更新：

```bash
curl -X PATCH http://localhost:3000/api/menu/1 \
  -H "Content-Type: application/json" \
  -d '{"price": 99, "version": 1, "changeReason": "舊版更新測試"}'
```

應該得到 409：

```json
{
  "error": "Menu item version mismatch"
}
```

## 測試 7：送出舊版訂單會回 409

流程：

1. 建立訂單。
2. 把目前菜單品項加入購物車。
3. 在送出前更新該菜單品項，讓購物車內的版本變舊。
4. 送出訂單。

預期結果：

```json
{
  "error": "Menu version mismatch: order contains stale item data",
  "details": {
    "staleItems": [
      {
        "id": 1,
        "name": "某品項",
        "orderedPrice": 40,
        "currentPrice": 45,
        "reason": "第一次調價"
      }
    ]
  }
}
```

## 測試 8：DELETE 是下架目前版本

```bash
curl -X DELETE http://localhost:3000/api/menu/13
```

預期：

- 該品項不再出現在 `/api/menu/current`。
- `/api/menu/:id/history` 仍可查到歷史版本。
- 舊訂單仍保留當時加入購物車的版本資料。

## 前端介面測試

登入示範帳號：

- Email：`demo@example.com`
- 密碼：`1234`

在早餐店介面中確認：

- 菜單卡片有顯示版本號與品項 ID。
- 調價後卡片會顯示舊價格與新價格。
- 點「編輯」可以建立新版本。
- 點「版本」可以查看完整版本歷史。
- 點「下架」會讓目前版本從菜單消失。
- 購物車內若含舊版本，會顯示價格變更或過期提示。
- 送出舊版訂單時，會跳出 stale item 細節。

## 完成檢查

- [ ] `/api/menu/current` 只回 current version。
- [ ] `PATCH /api/menu/:id` 會建立新版本。
- [ ] response 有 `previousPrice` 與 `changeReason`。
- [ ] `GET /api/menu/:id/history` 能查完整歷史。
- [ ] 舊版本更新會 409。
- [ ] stale order submit 會 409，且有 `details.staleItems`。
- [ ] 早餐店介面可以看見版本、歷史、調價、下架與 stale 提示。
