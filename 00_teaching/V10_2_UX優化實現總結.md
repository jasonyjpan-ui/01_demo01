# V10.2 完整版本化模型與早餐店介面實作總結

V10.2 現在採用「完整菜單版本化」模型：菜單品項更新時不覆寫舊資料，而是建立新的 current version，舊版本保留在歷史紀錄中。訂單項目會保存當下加入購物車的菜單版本，因此送出訂單時可以檢查是否已過期、是否調價、是否下架。

## 已完成範圍

### 1. 菜單版本欄位

`MenuItem` 已支援：

- `id`：實體資料列 ID，每個版本都有自己的 ID。
- `logicalId`：同一個菜單品項的穩定識別碼。
- `entityId`：跨資料庫/同步用途的穩定識別字串。
- `version`：版本號，從 1 開始遞增。
- `isCurrentVersion`：是否為目前版本。
- `supersedes`：此版本取代的上一版 ID。
- `previousPrice`：上一版價格。
- `changeReason`：變更原因。
- `createdAt` / `changedAt`：建立與變更時間。

### 2. API 行為

- `GET /api/menu` / `GET /api/menu/current`：只回傳 current version。
- `PATCH /api/menu/:id`：檢查 request body 的 `version`，成功後建立新版本。
- `GET /api/menu/:id/history`：回傳同一個 `logicalId` 的完整歷史。
- `DELETE /api/menu/:id`：下架目前版本，不刪除歷史。
- `POST /api/orders/:id/submit`：若購物車內含過期版本，回傳 409 與 `details.staleItems`。

### 3. Store 實作

JSON store 與 PostgreSQL store 都已支援同一套版本化行為：

- 新增品項會建立 version 1。
- 更新品項會建立 version + 1，並把舊版本標為非 current。
- 查詢菜單只顯示 current version。
- 歷史查詢會保留所有版本。
- 送出訂單會用 `logicalId` 找目前版本並比對 `version`。

### 4. 早餐店介面

前端已把 V10.2 功能顯示在早餐店操作流程中：

- 菜單卡片顯示 `v版本號`、品項 ID、調價提示、最近異動原因。
- 可在介面直接編輯品名/價格/變更原因，送出後建立新版本。
- 可開啟「版本歷史」視窗查看每一版價格、原因、取代關係。
- 可下架目前版本。
- 購物車會偵測價格變更與過期品項。
- 送出訂單遇到 stale item 會顯示舊價格、新價格與處理提示。

## 驗證結果

已執行：

```bash
npm run build
bun test
```

結果：

- 前端與後端 production build 通過。
- JSON store 版本化測試通過。
- 測試涵蓋新增 version 1、更新遞增版本、完整歷史、舊版更新 409、舊版訂單送出失敗。

## 學習重點

V10.2 的核心不是「多一個 version 欄位」，而是把菜單品項視為一條可追溯的版本線：

- 顧客看到的是 current version。
- 購物車保存的是當下選到的 specific version。
- 管理者更新菜單時建立新版本。
- 系統在送單時保護訂單價格與菜單狀態的一致性。

這就是完整版本化模型在早餐店情境中的最小可用實作。
